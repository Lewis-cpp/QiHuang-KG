# QiHuang-KG 架构设计

历史快照：本文保留原 SQLite 原型设计；当前技术栈、数据模型、范围与接口以[v2 架构](architecture.md)为准。

版本：1.0 · 设计日期：2026-10-04 · 状态：核心数据闭环已完成，进入查询实现

适用范围更新：本文件保留 SQLite 原型设计。最终交付必须满足 Vastbase、NoSQL、AI 和十万条以上数据，技术路线、范围与排期以[开发计划](development-plan.md)为准。当前使用 PostgreSQL 18.6 开发库，已有两源数据实际入库，最后迁移到 Vastbase。九类实体、七类关系、共享 v2 表结构及发布流程见[迁移运行说明](vastbase-import.md)；涉及存储与数据映射时以该说明为准。

本设计承接[项目范围分析](../project-scope-analysis.html)，面向中医药学习者，完成“检索知识 → 阅读详情 → 探索关系 → 核对来源”的学习流程。首版采用 **Vue 3 + TypeScript + Cytoscape.js、FastAPI、SQLite**：一个 Web 应用、一个后端进程、一份只读知识库，通过离线导入工具发布数据。

架构、建表脚本、结构审计及核心数据导入已完成。当前 SQLite 快照实际包含 599 条实体、1,286 条关系和 3,146 条证据；数据处理说明见[运行说明](data-processing.md)。应用接口与页面尚未实现，性能指标仍属于验收目标。未指定团队人数或交付日期，继续沿用范围分析中的单人毕业设计假设。

## 1. 范围与架构决策

| 决策 | 首版采用 | 理由与重新考虑条件 |
| --- | --- | --- |
| 系统形态 | 模块化单体，公开只读查询、命令行离线维护 | 六项核心功能共享数据与证据；出现独立团队或独立扩容需求后再拆服务 |
| 数据范围 | 本草典中药、方剂、证候、古籍四类实体 | 先完成一组数据的完整链路；其余五组数据按明确场景接入 |
| 存储 | SQLite 存实体、关系与证据，固定 SQL 查询一至两跳 | 599 个实体、有限关系足以用单库表达图模型；多实例在线写入时评估 PostgreSQL |
| 图谱 | 节点表与有向边表作为统一模型，浏览器渲染局部图 | 图谱能力由关系模型、查询及解释体现；不把图库软件作为项目成果的替代 |
| 数据发布 | 新文件构建、校验、停服切换、保留旧版本 | 避免原库被导入中断污染；首版允许短暂停机，不建设实时同步 |
| 中文搜索 | 规范化名称、可核实别名及字段子串匹配 | 不依赖分词服务；召回或延迟不达标后再评估中文分词和全文索引 |
| 问答与创新 | MVP 使用固定关系查询；后续优先可解释检索实验 I01 | 复用图谱和证据；大模型、向量库、规则推理均为后续可选项 |
| 用户体系 | 浏览无需登录，无线上写接口 | 出现在线维护或跨设备个人数据需求时再建设身份认证 |

不引入 Redis、消息队列、微服务、双库同步和通用工作流引擎。Vastbase、Neo4j 或智能问答若成为任务书硬性要求，按第 12 节调整；当前设计不假设这些约束已存在。

### 2.1 已发现的具体差异

- `zhu_ling_tang → ze_xie`：`formulas.json` 中角色为 `chen`，`relationships.json` 中为 `jun`，剂量均为 `9g`。组成边保留，`quality_state=conflicting`；共同剂量可显示，规范化角色为空，两项原始值随证据展示，等待人工确认。
- `xiao_jian_zhong_tang`：实体的 `source_text_key` 指向《伤寒论》，关系文件另记《金匮要略》。两条书目关联并存，不自动判断某条错误，不把“另有记载”解释为唯一首出。
- 35 条无法连接当前古籍实体的中药引文：原始段落和来源文字继续出现在中药详情中，标记“书目未关联”；不猜测古籍 ID，不创建带空名称的占位节点。
- `schema.json` 的审核枚举说明与实际数据不一致。导入器以显式兼容规则识别当前值；未知值保存原文并映射为 `unknown`，列入报告。

### 2.2 空值、别名与剂量

当前四份核心文件没有统一别名字段。首版提供别名表与查询能力，初始可为空；需要补充时使用带来源定位和人工确认记录的整理文件。不能把古籍注释中的词、炮制品名称或相近词自动当成等价别名。

缺失值使用 `null`，前端显示“来源未提供”。历史剂量按原始字符串展示，不统一折算古今单位，不根据通用剂量填补方剂剂量。四君子汤整理字段中的克数和古籍段落中的“各等分”分别引用各自位置；书中有该方不等于书中支持整理字段的全部数值。

## 3. 系统结构与技术栈

```text
学习者浏览器
  Vue 页面：检索目录 / 实体详情 / 局部图谱与关系查询 / 来源说明
                    │ 同源 HTTP JSON，携带 build_id
                    ▼
FastAPI 单体：输入校验 → 知识查询 / 图查询 / 证据查询 → 响应模型
                    │ 参数化 SQL，每请求独立只读连接
                    ▼
SQLite 发布快照：entity / alias / edge / evidence / source_record
                dataset / build
                    ▲ 离线生成并发布，Web 进程不写入
导入工具：原始文件 → 标准化 → 去重与证据映射 → 完整性检查 → 新快照
                    ▲
datasets/raw（只读）+ datasets/curated（人工整理，后续按需增加）
```

| 层次 | 技术与职责 | 约束 |
| --- | --- | --- |
| 页面 | Vue 3、TypeScript、Vite；Vue Router 管理四类页面 | 使用原生 `fetch`；暂不增加全局状态框架和大型组件库 |
| 图谱视图 | Cytoscape.js：节点、边、布局、缩放及点击事件 | 节点有形状和文字区分；同步提供可访问的关系列表 |
| HTTP 服务 | Python、FastAPI、Pydantic、Uvicorn | 校验参数与响应；OpenAPI 随实际路由生成，不手写第二套规范 |
| 数据访问 | Python 标准库 `sqlite3`，少量参数化 SQL | 不预建通用 Repository、ORM 或数据库适配器 |
| 导入与审计 | Python 的 `json`、`hashlib`、`pathlib`、`sqlite3` | 导入失败有明确退出码，生成机器可读问题清单 |
| 交付 | 前端构建产物由后端提供，单机单进程启动 | Node 仅在构建时使用；发布后无运行时 CDN 依赖 |

FastAPI 提供基于 OpenAPI 的接口说明与输入模型支持，适合把本设计契约落实为可验证路由。[官方功能说明](https://fastapi.tiangolo.com/features/)

SQLite 官方说明其适合本地存储及低写入并发场景，同一数据库同时只有一个写入者。将导入与在线只读服务分开，是本项目的设计选择，不是数据库性能承诺。[SQLite 适用场景](https://www.sqlite.org/whentouse.html)

`sqlite3` 支持参数绑定和 URI 方式打开数据库，使用 `mode=ro` 限制服务写入；每个同步路由在当前执行线程创建和关闭连接，不在不同请求间共享一个连接。[Python 官方文档](https://docs.python.org/3/library/sqlite3.html)

Vue 用于响应式页面，Cytoscape.js 专门承载图数据和交互。版本在实现启动时锁定到依赖锁文件；本设计不虚构“最新版本”。[Vue 官方说明](https://vuejs.org/guide/introduction.html)、[Cytoscape.js 官方文档](https://js.cytoscape.org/)

## 4. 模块边界与页面

| 模块 | 负责的输入与输出 | 对应范围 |
| --- | --- | --- |
| 离线导入 | 原始记录 → 数据快照、清洗报告、清单 | M01 |
| 知识查询 | 关键词、类型、ID → 列表、详情、已收录属性 | M02、M03 |
| 图与关系查询 | 中心实体、固定模板 → 节点、边、路径、证据 ID | M04、M05 |
| 证据查询 | 证据 ID → 数据集、文件、记录、字段值及引文 | M06 |
| Web 展示 | 页面状态与选择 → 请求；响应 → 文本、表格、局部图 | M02—M06 |

模块是同一进程中的普通文件和函数，不是独立服务。查询 SQL 只存在于后端；页面从 API 获取数据，不能直接读取原始目录或访问数据库。

| 路由 | 页面 | 必须覆盖的状态 |
| --- | --- | --- |
| `/` | 关键词检索、四类目录、类型筛选、分页 | 首次进入、加载、空结果、错误、返回后保留条件 |
| `/entities/:id` | 名称属性、组成或关联、来源与证据抽屉 | 缺失字段、角色冲突、未关联书目、实体不存在 |
| `/explore?center=…` | 一跳图、固定问题表单、路径解释 | 单节点、截断、继续展开、无路径、键盘可操作列表 |
| `/sources` | 数据集说明、审核标识含义、当前发布版本 | 原文与书目区别、来源说明、版本刷新提示 |

筛选条件存 URL；返回页面恢复条件，关键字输入提交后再请求。实体详情、图节点、查询结果共用名称和证据展示组件。关系边点击打开其证据列表；证据详情通过抽屉展示，不必增加独立页面体系。

## 5. 领域模型与存储设计

### 5.1 实体与关系

| 实体类型 | 规范化字段 | 保留的类型属性 |
| --- | --- | --- |
| `herb` 中药 | `key → source_key`、`name_zh → label` | 性味、分类、功效、主治、炮制、原始剂量与引文 |
| `formula` 方剂 | 同上 | 分类、治法、制法、描述；组成展示以规范化边为准 |
| `pattern` 证候 | 同上 | 主症、兼症、舌脉、病因病机；症状暂作属性 |
| `text` 古籍 | `key → source_key`、`title_zh → label` | 作者、朝代、年份、段落、译文和注释 |

| 关系 | 固定方向 | 来源映射 | 属性与解释 |
| --- | --- | --- | --- |
| `CONTAINS` | 方剂 → 中药 | `composition[]` 与反向转换的 `herb_in_formula[]` | `role`、`dosage_raw`、`position`；冲突字段不择一覆盖 |
| `ASSOCIATED_WITH_PATTERN` | 方剂 → 证候 | `formula_treats_pattern[]` | 页面显示“关联证候”；仅表示来源记录的知识关联 |
| `CITED_IN` | 方剂或中药 → 古籍 | 方剂 `source_text_key`、`formula_cited_in_text[]`、可解析的中药 `classical_references[]` | 只承诺书目关联；具体字段是否有原文支持由证据决定 |

原始 `formula_treats_pattern` 名称保存在来源记录中；规范化关系避免将资料中的关联呈现为临床效果保证。所有关系有向保存；反向查询使用目标端索引，不重复插入反向边。

### 5.2 七张表及关联

[建表脚本](schema.sql)是本设计的物理结构依据，可在 SQLite 中直接执行。

```text
dataset 1 ── N source_record 1 ── N evidence
   │                 │                  │
   └── N entity ─────┘                  ├── N:1 entity（实体证据）
            │                           └── N:1 edge（关系证据）
            ├── 1:N alias ── N:1 source_record
            └── 1:N edge(source_id / target_id)

build：每份数据库恰好一条发布清单；导入完成后校验数量。
evidence：每条只关联一个 entity 或一个 edge，不同时关联两者。
```

| 表 | 主要字段 | 唯一性和职责 |
| --- | --- | --- |
| `build` | `id`、`schema_version`、`transform_version`、`created_at`、`manifest_json` | 清单含所有输入哈希、规则版本、行数、异常摘要 |
| `dataset` | `id`、标题、来源版本、URL、许可声明、署名 | 逐来源登记；声明来自本地材料，公开分发前核对原始条款 |
| `source_record` | 来源、文件、文件哈希、记录键、记录位置、原始对象 JSON | 唯一 `(dataset_id, filename, record_key)`；支持离线追溯 |
| `entity` | 类型、稳定 ID、源键、名称、分类、检索字段、属性 JSON、审核原值、来源记录 | 唯一 `(dataset_id, type, source_key)`，名称可以重复 |
| `alias` | 实体、别名、规范化别名、来源记录、字段路径 | 同名可指向多个实体，保留歧义；只收录已核对映射 |
| `edge` | 两端 ID、关系类型、属性 JSON、质量状态 | 唯一 `(source_id, relation, target_id)`，证据独立合并 |
| `evidence` | 实体或边、来源记录、字段路径、证据类别、摘录 | 一项主张可有多条证据；引文必须有非空摘录 |

高频筛选字段独立建列；嵌套且暂不筛选的属性保存在 JSON 文本中。`source_record.content_json` 保存原对象，`attributes_json` 保存页面需要的规范化属性；不得在 UI 中绕过冲突规则直接用原始 composition 作为确定结论。

### 5.3 ID、索引与一致性

- 实体 ID 为 `数据集命名空间:类型:源键`，例如 `bencaodian:formula:si_jun_zi_tang`。只有数据集与类型内的源键可用于身份判断，同名实体不自动合并。
- 边 ID 为 `edge:` 加规范化三元组 JSON 的 SHA-256。三元组格式固定为 `[source_id, relation, target_id]`，UTF-8、无多余空白；属性变化不改变边 ID。
- 来源记录有源键时使用源键；无源键关系对象使用排序键、固定分隔符的对象 JSON 哈希。`record_locator` 保存整份文件中的 JSON Pointer；文件哈希变化后定位必须重新校验。
- 证据 ID 由目标实体或边 ID、来源记录 ID、`field_path`、类别计算哈希。`field_path` 是相对于原始对象的 JSON Pointer，空字符串表示整个对象；不会误用为整份文件的行号。
- `entity(name_norm)` 支持精确名称匹配；`alias(name_norm, entity_id)` 支持别名；`edge(source_id, relation, target_id)` 和反向索引支持邻接查询。子串检索仍会扫描，当前规模可接受，不能宣称普通索引加速任意中文模糊查询。
- 每个数据库连接启用外键。DDL 限定三种边的端点类型及证据唯一归属；发布前再检查实体与原始记录属于同一数据集、JSON Pointer 可解析、每条边有证据。

数据集跨文件同键不冲突，来源记录 ID 同时包含来源及文件身份。未来换数据源只新增命名空间；跨来源对齐通过显式映射表示，不改写原始实体身份。

## 6. 导入、校验与发布流程

### 6.1 一次完整构建

1. 为核心五份输入文件、实际使用的来源元数据和所有整理文件计算 SHA-256，连同 schema/转换规则版本生成 `build_id`。同样输入和规则版本得到同一 ID。
2. 只读解析原始文件。四类实体要求源键唯一、名称非空；没有源键或不能解析的核心文件导致构建失败。
3. 写入新临时 SQLite 文件的 `dataset`、`source_record`、`entity`。标准化只作用于处理结果；原文件不变。
4. 展开三个关系类型、检查端点、按三元组去重；合并证据。组成边的 `position` 取实体 composition 的数组下标，只有关系文件提供时按目标 ID 排序并保留“未提供原始顺序”标识。
5. 比较重复主张的角色和剂量。完全相同则合并；值不同则该字段设空、边记冲突、两项原值保留；一方缺失则采用已提供值，同时保留缺失来源，不把它误标成一致支持。
6. 把原文和来源信息写入证据。35 条无法关联古籍的中药引文挂在中药实体上，输出 `unresolved_reference`，不为其插入悬空边。
7. 完成事务后校验外键、图端点类型、证据覆盖、字段定位、计数与清单。执行 `PRAGMA integrity_check` 和 `PRAGMA foreign_key_check`，确认 `build` 恰好一条。
8. 输出新快照、发布清单和问题报告。运行固定查询用例；只有全部硬性检查通过，且本批已知警告与审核清单一致，才允许发布。
9. 首版进入短暂维护窗口：停止服务，把新文件放入 `var/releases/<build_id>/kg.sqlite`，以新的绝对路径重启服务；验证 readiness 和演示链路，失败则恢复旧路径。

同一快照重复构建是重建，不是向旧库不断追加。发布文件不可覆盖；同一 `build_id` 已存在时校验清单并复用。应用数据一致及 ID 一致是幂等标准，不要求生成时间或 SQLite 文件字节完全相同。

### 6.2 失败等级

| 情况 | 动作 | 对外可见结果 |
| --- | --- | --- |
| JSON 损坏、重复源键、必填字段缺失、未知关系映射 | 终止构建，临时产物不发布 | 在线版本继续可用 |
| 核心组成或证候关系端点不存在 | 终止构建，报告原始位置 | 不插入孤立边 |
| 引文未提供古籍键、古籍未在首版收录 | 保留实体证据，报告警告 | 显示原文及“书目未关联” |
| 重复主张属性冲突 | 保留边，冲突字段为空，记录双方证据 | 显示“存在差异，待核对” |
| 同一方剂有多条古籍记载 | 保留多条合法书目关联 | 并列展示，区分字段出处 |
| 新增未识别审核状态 | 保留原始值，规范化为 `unknown`，报告警告 | 显示“审核状态未识别” |

问题报告至少含 `severity`、`code`、`filename`、`record_key`、`field_path`、`raw_value`、`action`；不得只输出“跳过若干条”。当前已知警告应按具体记录与字段登记，不能用“允许任意 35 条错误”这样的数量豁免。

### 6.3 来源与证据的层级

来源链为：**页面中的属性或关系 → evidence → source_record → dataset 与输入文件哈希**。读者可以定位到本地原始对象及字段。

`curated` 表示数据集整理内容；`source_quote` 表示数据集中提供的原文摘录，不代表本项目已核对原版影印本；`bibliographic` 只支持书目关联。`auto_extracted` 与 `rule_inferred` 为后续来源预留类别，首版不生成此类主张。来源审核状态与证据类别是两个维度，不能由“编辑审核”推导出“原文已核验”。

古籍条目中的任意段落不能自动作为该书关联的所有药物或剂量的证据。只有来源中存在明确记录定位或人工核对的映射时，才将具体段落关联到对应主张。

## 7. 检索、图查询与解释

### 7.1 检索规则

查询词执行 Unicode NFKC、去首尾空格及英文大小写折叠；展示原文不变。对名称、别名、拼音、英文名及白名单描述字段构建规范化搜索文本，原始 JSON 字段名、ID、网址和剂量不混入全文匹配。

排序采用明确优先级：名称精确命中 → 已审核别名精确命中 → 名称或别名前缀命中 → 名称、别名或搜索文本子串命中；同级按 `label, id` 稳定排序。返回命中字段及文本，不计算没有标定意义的“医学相关度”。搜索先以实体去重，再分页，防止多个别名让结果重复。

`q` 空缺或清理后为空时展示目录；非空长度上限 100 字符。`page_size` 默认 20、上限 50，`page` 为正整数。`LIKE` 中的 `%`、`_` 和转义符作为文字处理，同时使用 SQL 参数绑定；查询列与排序方式只能从固定白名单选择。输入不能直接拼接成 SQL。

### 7.2 一跳图

中心实体查出入边，默认包括全部三个关系类型，按关系类型、邻居名称、边 ID 排序。服务端一次最多返回 50 个节点（含中心）、100 条边；端点必须都包含在返回节点集合中。查询最多读取上限外一条候选边，以判断是否截断；若节点预算先耗尽，也标记截断。

返回 `truncated` 和限制值；不把局部边数叫作全图总数。不支持请求任意深度。用户点击节点展开即发起另一条一跳请求，前端按 ID 合并；当前画布上限 100 节点、200 边，达到上限提示清空或切换中心。展开和清空都能从关系列表操作，颜色不是唯一标识。

### 7.3 固定查询模板

| `template` | 输入类型 | 路径 | 展示 |
| --- | --- | --- | --- |
| `formula_herbs` | 方剂 | 方剂 → `CONTAINS` → 中药 | 组成、原始剂量、角色与证据；按 position 排序 |
| `herb_formulas` | 中药 | 中药 ← `CONTAINS` ← 方剂 | 收录该药的方剂与证据 |
| `formula_patterns` | 方剂 | 方剂 → `ASSOCIATED_WITH_PATTERN` → 证候 | 关联证候及来源 |
| `herb_patterns_via_formula` | 中药 | 中药 ← 方剂 → 证候 | 两跳的完整节点、边和每条边的证据 |

前三个满足 M05 最低要求，第四个提供两跳演示。两跳是两个边表联接，按完整路径去重；同一证候经不同方剂连接时保留不同路径。结果分页默认 20、上限 50，按路径 ID 元组稳定排序。没有路径返回空列表。

两跳解释只能说“该药出现在某方剂中，该方剂在来源数据中关联某证候”，不能直接生成“该药治疗该证候”这一新边。路径查询只接受模板名和实体 ID，不暴露任意 SQL、Cypher 或规则表达式。

## 8. HTTP 接口契约

所有业务接口使用 `/api/v1`、UTF-8 JSON。以下为待实现契约；实现时由 FastAPI 响应模型生成 OpenAPI，并用契约测试验证。公开读接口使用 GET，不设置注册、上传或管理写接口。

| 方法与路径 | 参数 | 响应主体 |
| --- | --- | --- |
| `GET /entities` | `q?`、`type?`、`page=1`、`page_size=20` | 实体摘要列表、命中信息、分页 |
| `GET /entities/{id}` | 完整实体 ID | 实体类型、名称、属性、审核状态、实体证据 ID；组成通过固定查询获取 |
| `GET /graph` | `center`、`relation?` | `nodes[]`、`edges[]`、`truncated`、限制值；边含质量状态及证据 ID |
| `GET /relation-queries` | `template`、`entity_id`、分页参数 | `paths[]`：有序节点 ID、边 ID、解释；附本页节点和边字典 |
| `GET /evidence/{id}` | 证据 ID | 原始字段值、摘录、证据类别、记录定位、文件哈希、数据集摘要 |
| `GET /datasets` | 无 | 来源名称、版本、署名、原始许可声明及当前快照摘要 |
| `GET /health/live` | 无 | 进程可服务，`200` |
| `GET /health/ready` | 无 | 数据库可读、schema 受支持、清单有效；正常 `200`，否则 `503` |

业务接口均接受可选 `build_id`。首次读取不传，响应 `meta.build_id` 后前端在后续请求中携带；若已发布新版本，后端返回 `409 snapshot_changed`，前端清空旧图和证据缓存并提示刷新。不能把旧详情与新证据静默混在一起。健康检查无需快照参数。

### 8.1 通用响应

成功响应为 `data` 加 `meta`；分页响应包含 `page`、`page_size`、`total`，这里的 `total` 指去重后符合条件的结果数。图响应不提供未经计算的 `total`。下面是结构示例，示例发布 ID 不是已运行系统的 ID。

```json
{
  "data": {
    "id": "bencaodian:formula:si_jun_zi_tang",
    "type": "formula",
    "label": "四君子汤",
    "review_status": "editor_reviewed",
    "review_status_raw": "editor-reviewed"
  },
  "meta": {
    "build_id": "example-build-id",
    "request_id": "example-request-id"
  }
}
```

节点最小字段为 `id,type,label`；边最小字段为 `id,source_id,target_id,relation,properties,quality_state,evidence_ids`。实体详情另外含 `attributes,evidence_ids`。路径解释引用真实边 ID，不能只返回一段无法回查的文字。

证据详情至少含 `id,kind,field_path,raw_value,excerpt,source_record,dataset`。其中 `source_record` 为 `id,filename,record_key,record_locator,file_sha256`；文件名只返回数据集内相对路径，不暴露服务器绝对路径。正文由数据库中保存的原始对象解析得到，不允许客户端传文件路径让服务读取任意本地文件。

### 8.2 错误与边界

统一错误体为 `{"error":{"code":"…","message":"…"},"meta":{"request_id":"…","build_id":"…"}}`；数据库未就绪时 `build_id` 可以为空。

| 状态 | 错误码 | 触发与页面动作 |
| --- | --- | --- |
| `404` | `entity_not_found` / `evidence_not_found` | ID 不存在，显示返回入口 |
| `409` | `snapshot_changed` | 版本不一致，提示刷新并重新查询 |
| `422` | `invalid_query` | 无效类型、模板、页码、过长输入或模板实体类型错误 |
| `503` | `knowledge_unavailable` | 数据库损坏、丢失、版本不支持或查询超时，提示稍后重试 |
| `500` | `internal_error` | 意外异常，对外隐藏栈和本地路径，日志保留 request_id |

实体存在但搜索或关系无结果返回 `200` 和空列表，不返回 `404`。FastAPI 默认校验错误需要转换为上述错误格式；未知 `/api/*` 返回 JSON 404，不能被 SPA 的页面回退规则吞掉。

## 9. 一条完整查询链路

```text
浏览器                    FastAPI                 SQLite
输入“四君子汤” ────────→ 名称匹配 ──────────────→ entity
显示结果及 build_id ←─── 摘要与审核标识 ←──────── 查询结果
打开详情 ──────────────→ 实体与属性 ────────────→ entity + source_record
查看组成 ──────────────→ formula_herbs ─────────→ edge + entity + evidence
打开局部图 ────────────→ 查询出入边 ────────────→ 有端点上限的子图
点击证据 ──────────────→ 解析原始字段路径 ──────→ evidence + source_record + dataset
显示原文/书目/整理字段 ← 证据类别与精确定位 ←──── 原始值和输入文件哈希
```

每次业务请求均独立连接到同一已发布快照。应用层只使用规范化边回答组成和关系问题，原始记录用于解释与对照。前端不能根据两次不同接口的字符串名称自行推断实体相同。

## 10. 部署、可靠性与安全边界

### 10.1 首版部署

本地开发为 Vite 开发服务代理 `/api` 到 FastAPI；发布时构建前端静态资源，Uvicorn 启动一个进程，由 FastAPI 提供 `/assets`、业务 API 和 SPA 页面。同源部署避免额外跨域配置。应用路由优先于 SPA 回退；深链接刷新返回页面入口。

只配置确实会变的值：`KG_DB_PATH` 指向发布快照绝对路径，`KG_LOG_LEVEL` 控制日志；监听地址和端口由启动参数提供。Node 和联网下载只在准备构建时需要，已构建系统在断网状态下完成六项 MVP 功能。若需要离线接口文档，Swagger UI 资源也需随包保存。

演示环境默认只监听本机。需要公开访问时在反向代理配置 HTTPS、请求速率和访问日志，数据库文件及 `datasets/raw` 不作为静态目录暴露。首版不要求容器；若交付方需要 Docker，再以同一应用和只读数据卷打包。

### 10.2 故障与恢复

- 数据服务启动时验证文件存在、schema 版本和清单，失败时 readiness 为 `503`；不会自动新建空数据库假装启动成功。
- 连接以 `mode=ro` 打开，并启用 `query_only` 和外键。同步路由每请求独立连接；查询设 2 秒执行预算，可用 SQLite progress handler 中止超时工作，返回明确错误。
- 发布允许短暂不可用。保存当前和上一份完整快照、清单与处理规则；切换失败就使用旧路径重启。备份包括整理文件，避免人工确认记录丢失。
- 日志记录 request_id、路由模板、状态码、耗时、build_id；不默认记录用户完整搜索词，不记录病历信息。性能统计区分成功响应和超时，不能删除超时样本后报告漂亮的 P95。

### 10.3 输入与内容边界

所有类型、关系、查询模板和排序字段使用白名单；数值范围由服务端校验。用户输入和数据集文本均按纯文本渲染，不使用 `v-html` 拼接。外链只接受 HTTP/HTTPS，打开新标签时使用隔离属性。

系统展示已有知识、来源和历史记录，不接收个体病例、不生成个体处方。这个范围来自既有范围分析，而不是额外新增的产品流程。未来若有在线写接口，身份认证、权限检查与修改审计必须随该接口一起交付。
